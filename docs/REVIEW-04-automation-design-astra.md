I would resolve items 1–8 before implementing the transports. References to `src/core` below follow the in-progress moves from `src/renderer/src/pdf`.

1. **Live-document routing can lose edits or change command meaning.** §§14.3–14.4 automatically switch between disk and session depending on dirtiness. A clean saved document still has editable annotations/history; reloading it loses those. Checking dirtiness before writing also races with user edits. Require an explicit target—`file` or `documentId`—plus expected revision/hash. Coordinate open-file writes before committing, under the document lock; define whether `--out` exports or changes the live session. See [app.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/store/app.ts), [documents.ts](/Users/aeedpuganti/Code/yonderPDF/src/main/documents.ts).

2. **Forwarding store actions is not a usable automation backend.** §14.4 actions commonly depend on the active tab, open dialogs, swallow errors into toasts, or silently return when busy. Concurrent requests could affect the wrong document or report false success. Extract parameterized document services with explicit IDs, typed results, locks, editor flushing, revision checks, and noninteractive policies. UI and registry should both call those services. See `Actions` and `save`, `deletePages`, `insertFromFile`, `print` in [app.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/store/app.ts).

3. **Socket security assumes platform facilities that Node does not expose directly.** §§14.1.6/14.5 specify peer-UID checks and a Windows DACL without selecting an implementation. Public `node:net` does not provide those controls. Windows pipes also support remote clients; the local-looking name does not establish the promised network boundary. Select and audit a native transport/helper, enforce the SID ACL and remote-client rejection, and test cross-user access before promising this security model. [Node API](https://nodejs.org/api/net.html), [Windows pipe controls](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea).

4. **Token discovery and socket lifecycle are missing.** §§14.4–14.5 never explain how CLI/MCP obtain the per-launch token or authenticate the endpoint. Specify a private directory, owner-only discovery file, atomic publication, authenticated handshake timeout, restart behavior, and ownership-checked stale-socket cleanup. Separate development/production profiles; accommodate UNIX socket path limits. Never expose tokens through argv, logs, renderer state, or schema output. A readable same-user token is not protection against another process running as that user.

5. **The new bridge could undo the renderer’s path restriction.** §14.4 must distinguish privileged external commands from renderer-callable commands. Do not expose a generic registry invocation through preload that accepts arbitrary input/output paths. Main should resolve paths into request-scoped capabilities; renderer replies should carry only validated results/bytes. Validate reply frame, request ID, document ID and lifecycle, including renderer crashes. Preserve the sandbox settings in [index.ts](/Users/aeedpuganti/Code/yonderPDF/src/main/index.ts) and guards in [ipc.ts](/Users/aeedpuganti/Code/yonderPDF/src/main/ipc.ts).

6. **Running headless commands directly in main is unsafe for availability.** §14.4 moves PDF parsing, writing, image decoding and potentially catastrophic regex execution onto the window/IPC event loop. “No DOM” does not mean isolated or cheap. Run heavy work in cancellable workers/processes, with input, decoded-pixel, memory, time and concurrency limits. Bound every incoming JSON frame before parsing; the 16 MiB rendering-output limit in §14.5 does not address request exhaustion.

7. **The forms plan contradicts the existing save contract.** §§14.1.5/14.2 replace pdf.js form serialization with pdf-lib, despite §12 findings 15–16 explicitly choosing pdf.js appearances. [app.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/store/app.ts) uses `annotationStorage` and `saveDocument()`. Use one shared form backend or explicitly withdraw parity and test the differences. Specify typed values, checkbox/radio export values, multiselect arrays, read-only fields and multiple widgets per field; `name=value` strings are insufficient.

8. **Headless commands bypass important document guards.** §§14.3–14.5 omit password handling, encrypted-document read-only behavior, signature-invalidation consent, and lossy-operation acknowledgement. Expose document capabilities and structured errors; accept passwords through a protected input channel. Require explicit policy for rewriting signed documents and report form/bookmark loss from copy-based operations. Do not treat `ignoreEncryption` as decryption. See §§12–13 and `save`, `merge`, `extractPages` in [app.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/store/app.ts).

9. **The command table does not meet “every feature.”** §14.3 lacks annotation update/move/resize/restyle/text editing; undo/redo; annotation/page selection and select-all; Save As and close-all; date stamps; saved-signature list/add/remove/use; signature drawing/background removal; recent-file list/open/clear; tool/default-style settings; zoom/fit/actual size; view rotation; page navigation; sidebar/theme/signer settings; find-next/previous; and help/update controls. Add a coverage matrix against `Actions`, `MenuCommand` and `YonderAPI`, with explicit mappings or justified exclusions for internal callbacks. See [app.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/store/app.ts), [api.ts](/Users/aeedpuganti/Code/yonderPDF/src/shared/api.ts).

10. **Annotation removal and flattening overpromise persistent editing.** §14.3’s standalone commands reload saved annotations as read-only; `writeAnnotations(bytes, [], {flattenAnnotations:true})` does not flatten existing annotations. Images are already flattened and cannot be listed as editable image annotations. Return provenance and `editable`/`removable` capabilities; reject unsupported removal/flattening explicitly. Provide persistent sessions or batch-local annotation IDs for follow-up edits. See §13 and [writer.ts](/Users/aeedpuganti/Code/yonderPDF/src/core/writer.ts).

11. **Text anchors are not yet reliable placement geometry.** §§14.1.3/14.3 promise quads, but [search.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/pdf/search.ts) estimates axis-aligned rectangles using proportional character widths; it does not implement regex search or reliable rotated/vertical text geometry. The writer also reduces markup to axis-aligned bounds. Define normalization, reading order, occurrence numbering and ambiguity errors; return revision-bound match IDs, geometry quality and truncation status. Require explicit selection when several matches exist, and specify anchor offsets/alignment for signatures, notes and shapes.

12. **Page ranges cannot express reordering as proposed.** §14.3 reuses `parsePageRanges`, which sorts, deduplicates and normalizes descending ranges: `3,1,2` becomes `1,2,3`. Give reorder a separate ordered permutation schema and validate uniqueness/completeness. Also reject invalid page indices, empty geometry, nonfinite numbers and malformed colors before reaching writers that currently skip some invalid inputs. Define insertion-before/after and beginning/end explicitly. See [pageOps.ts](/Users/aeedpuganti/Code/yonderPDF/src/core/pageOps.ts), [types.ts](/Users/aeedpuganti/Code/yonderPDF/src/core/types.ts).

13. **Batch “single load/save” requires a different engine interface.** §14.3 cannot deliver that using current byte-in/byte-out page operations: each loads and saves independently. “Any commands above” also includes multi-output split, multi-input merge and printing. Introduce a transaction/session abstraction, restrict batch operations, define page references after earlier operations, and commit once after complete validation. Specify rollback, failing-operation index and one undo entry for live batches.

14. **File identity and overwrite policy need definition.** §§14.3–14.4 and [documents.ts](/Users/aeedpuganti/Code/yonderPDF/src/main/documents.ts) currently rely on path-string equality. Resolve relative paths in the caller’s context; account for symlinks, case aliases and hard links when detecting an open file. Reject existing outputs unless explicitly allowed, including `--out` aliases of `--in`. Add expected-file hashes, safe split naming, collision handling and a symlink policy. Atomic rename prevents partial files, not concurrent lost updates.

15. **Typed signatures cannot use the existing image pipeline as described.** §14.3 proposes rendering a signature through pdf-lib without canvas, but pdf-lib writes PDF content; it does not produce the PNG required by `ImageAnnotation` and the signature library. Choose a shared vector-signature model or a shared rasterizer. Custom-font embedding also requires `@pdf-lib/fontkit`, absent from `package.json`; package compatible font files and unify font IDs with [signature.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/pdf/signature.ts). [pdf-lib font requirements](https://github.com/Hopding/pdf-lib/blob/master/README.md#embed-font-and-measure-text).

16. **pdf.js needs distinct Node/browser adapters.** §14.2 cannot reuse [pdfjs.ts](/Users/aeedpuganti/Code/yonderPDF/src/renderer/src/pdf/pdfjs.ts), which depends on `document.baseURI` and Vite’s worker URL import. Installed pdfjs-dist 6.3.289 is ESM, declares Node engine requirements, and recommends its legacy build in Node. Package and test worker/CMap/font/WASM paths in the actual ASAR layout; decide native-canvas dependency handling explicitly. Node rendering is possible, so “app-only rasterization” should be a product decision, not a claimed pdf.js limitation.

17. **MCP cannot simply return CLI JSON.** §14.4 needs initialization/capability negotiation, SDK transport handling, `structuredContent`/`content` and `isError` mapping. Reserve stdout exclusively for protocol messages: the default pdf.js import printed a warning to stdout in my Node probe. Route diagnostics and deprecations to stderr. Resource links need implemented reads, MIME types, bounded content and lifetimes; merely returning a temp path is insufficient. Test actual client image/resource consumption. [MCP transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [tool results](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

18. **The proposed electron-vite target does not exist.** §14.2 describes a separate electron-vite “node” target; electron-vite 5’s configuration exposes `main`, `preload` and `renderer`. Use a separate Vite/Rollup library configuration or an explicitly configured additional entry. Specify ESM/CJS output, dependency externalization, asset copying and output-directory cleanup. Wire core/CLI/MCP typechecks into CI; absence of the DOM lib alone does not verify runtime portability. See [electron.vite.config.ts](/Users/aeedpuganti/Code/yonderPDF/electron.vite.config.ts), [supported configuration](https://electron-vite.org/config/).

19. **`ELECTRON_RUN_AS_NODE` creates an explicit hardening tradeoff.** §14.4 requires `RunAsNode` enabled; disabling that fuse breaks the shim. Document the decision and test the actual signed binary, stdin/stdout, exit codes and packaged entry resolution. Sanitize inherited Node/debug options and unset `ELECTRON_RUN_AS_NODE` when launching the GUI from the CLI. If the release requires disabling RunAsNode, choose a separate runtime/helper architecture now. [Electron fuse behavior](https://www.electronjs.org/docs/latest/tutorial/fuses).

20. **macOS installation is underspecified and notarization is currently disabled.** §14.4 promises a notarized shim, but [electron-builder.yml](/Users/aeedpuganti/Code/yonderPDF/electron-builder.yml) has `notarize: false` and no shim `extraResources` entry. Package executable permissions before signing, notarize/staple, and test a quarantined download on a clean machine. Offer `~/.local/bin`; `/usr/local/bin` may require narrowly scoped elevation. Resolve symlinks correctly, quote paths with spaces, preserve existing commands, and support uninstall/repair after app moves or updates. Do not install a persistent link into a mounted DMG. [Electron notarization](https://github.com/electron/notarize).

21. **Windows/Linux need real launcher and installer work.** §14.4’s PATH checkbox requires NSIS customization and uninstall cleanup. A `.cmd` launcher is not directly executable by every subprocess/MCP host; test the supported launch configuration or ship a console launcher. Verify stdout and exit codes from the packaged Windows executable. On Linux, integrate the deb launcher without replacing the GUI launcher; AppImage `--cli` needs dispatch before GUI startup and must preserve streams/signals. Add these artifacts and tests to [electron-builder.yml](/Users/aeedpuganti/Code/yonderPDF/electron-builder.yml).

22. **Agent retries need explicit safety semantics.** §§14.1–14.5 lack idempotency keys, expected revisions, dry-run and durable operation status. A disconnected response after a successful highlight otherwise causes duplicate annotations on retry. Add request deduplication with a documented lifetime, `--dry-run` returning resolved targets/warnings, and results containing target identity, revision/hash, created IDs and outputs. Define close-with-dirty policy, job cancellation, startup timeout and `APP_NOT_RUNNING`; never silently fall back to disk after live-session routing fails.

23. **Protocol/output details need a contract.** §14.4’s JSON-RPC example omits `"jsonrpc":"2.0"`; §14.1’s error shape needs transport-specific adaptation. Define numeric RPC errors with stable application codes/hints in `data`, CLI exit codes, notification subscriptions and sequence numbers. Paginate text/find/annotation results. Store artifacts in private directories with owner-only permissions, quotas and expiry. Add `render` and `app.reload` to the registry or remove their unregistered references. Separate structured input from `--json` output mode.

24. **Byte identity and current tests are inconsistent.** §14.1.5 promises byte-identical output; §14.6 explicitly avoids byte comparisons. `writer.ts` sets modification time, and annotation IDs/timestamps and form/signature backends differ. Promise semantic/visual parity instead, or inject deterministic metadata and IDs. Test form values, appearances, rendered geometry and preservation—not merely object counts and `/AP` presence.

25. **Reorder A1–A4 around the unresolved risks.** §14.7 should start with packaged-runtime/stdio and secure-transport feasibility spikes. Add shared document transactions, noninteractive policies and feature coverage before declaring A2 complete. Prototype MCP during A2 so schemas/resources influence the registry. A3 needs cross-platform authentication, concurrency, restart, renderer-crash and installer tests. Isolate `userData` in [cdp.mjs](/Users/aeedpuganti/Code/yonderPDF/scripts/e2e/cdp.mjs) so tests cannot hit a user’s running instance. Expand fixtures to encrypted/signed PDFs, forms, rotated/CropBox/UserUnit pages, malformed inputs and Unicode; explicitly schedule migration of UI callers to the registry.
