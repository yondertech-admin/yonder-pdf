1. **Blocker — Signing has no incremental PDF writer (§§3, 7).** Installed pdf-lib 1.17.1 `PDFDocument.save()` fully serializes the document; `useObjectStreams: false` does not make it incremental. `node-forge` produces cryptography, and `@signpdf/signpdf` signs prepared placeholders; neither supplies the missing general revision writer. Select and validate an incremental-writing engine before committing to multi-party signatures. [Signing APIs](https://github.com/vbuch/node-signpdf)

2. **Blocker — Signature validity rules contradict sequential signing (§7.2).** Later incremental signatures need not invalidate earlier signed revisions; unauthorized changes to the current document require separate detection. Appending a completion page can violate certification permissions. Define permitted changes, field locks, revision verification, and finalization rules; prepare completion content before signing or make it a separate signed artifact.

3. **Blocker — “Completed · all signatures valid” is unsupported (§7).** Self-signed certificates and typed email addresses establish no independently verified identity. Editable JSON cannot establish completion. Derive status from verified signatures and signed recipient/key bindings; separately display integrity, identity trust, revision coverage, and unavailable revocation information.

4. **Major — PAdES requires more than detached PKCS#7 (§7.2).** Specify PAdES-B-B requirements, including appropriate signature subfilter and signed attributes. Local timestamps are untrusted; offer optional trusted timestamping and validation evidence for stronger profiles, with explicit offline limitations. Validate using independent tools. [ETSI standard](https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf)

5. **Major — Signing evidence and key custody are incomplete (§7).** Local `viewed` events are assertions, clocks can be changed, and JSON/XMP copies can disagree. Use one canonical, versioned manifest, cryptographically bind events to revisions, protect private keys with OS-backed encryption, and define backup/recovery. A completion-page hash must identify an earlier revision or defined byte ranges, not ambiguously hash itself.

6. **Major — Legal workflow requirements are missing (§7).** No-server signing is not inherently invalid, but consent, intent, attribution, and record retention need explicit treatment. Add an affirmative signing declaration, applicable consumer electronic-record disclosures/consent, and retainable copies; define supported jurisdictions and excluded transactions. [US E-SIGN requirements](https://uscode.house.gov/view.xhtml?req=%28title%3A15+section%3A7001+edition%3Aprelim%29)

7. **Major — “Send” cannot attach files as specified (§7.3).** `shell.showItemInFolder()` only reveals a file; `mailto:` has no portable attachment mechanism and conflicts with the HTTPS-only shell policy. Electron 44 provides macOS `ShareMenu({ filePaths })`; use that, plus explicit export/manual attachment elsewhere. Define forwarding, duplicate/fork detection, and final-copy redistribution; delivery tracking, reminders, and globally synchronized status must be deferred.

8. **Major — Flattening does not secure signatures (§4.3).** A flattened image can still be extracted, replaced, or covered; the design also keeps its placement editable after saving. Describe Phase 1 as visual signing only. Cryptographic signing must explicitly finalize the signed revision.

9. **Major — The save model lacks a transactional revision boundary (§4.3).** Retaining `formBytes` avoids duplicate new annotations, but disk bytes, editable state, and the pdf.js proxy now differ. Serialize operations per document, capture immutable save revisions, rebase the proxy/storage consistently, and mark clean only after successful disk commit. Concurrent edits must remain dirty.

10. **Major — pdf.js can detach the canonical bytes (§4.1).** In installed 6.3.289, `getDocument({ data })` generally transfers typed-array storage to its worker. Passing `baseBytes` directly can break saving and shared history. Retain immutable canonical bytes and pass a dedicated copy to pdf.js.

11. **Major — Existing annotations have no edit/import path (§§4.2–4.3).** Saved annotations return inside `baseBytes`, outside the editable model. Implement import, stable PDF-object identity, replacement, and deletion tombstones; otherwise explicitly limit editing to annotations created during the current session. Define flattening for existing annotations too.

12. **Major — pdf-lib is not a high-level annotation engine (§4.3).** Version 1.17.1 lacks convenient creators/flatteners for the listed markup types; page drawing methods create content, not annotation objects. Budget a low-level writer covering dictionaries, appearance resources/transforms, flags, quads, opacity, and popups. Appearance streams improve interoperability but cannot guarantee identical rendering.

13. **Major — Page-index remapping is insufficient (§4.4).** `copyPages()` copies page objects, not the document’s complete AcroForm, outline, destination, or structure-tree organization. Merge/extract can orphan widgets or lose navigation; deletion can leave dangling references. Use stable page identities and explicit document-structure repair, field-name collision handling, and remapping of signatures and workflow fields.

14. **Major — Coordinate assumptions fail on valid PDFs (§4.1).** User-space units are not always physical points; CropBox origins can be nonzero/negative, and `/UserUnit` changes scale. Preserve raw PDF coordinates, combine intrinsic `/Rotate` with view rotation, transform every quad corner, and separate CSS viewport scale from canvas device-pixel scaling. Define CSS’s 96 px/in versus PDF’s default 72 units/in.

15. **Major — Form support needs a compatibility contract (§§2, 4.5).** The installed `TextLayer` and `AnnotationLayer` APIs exist, but layers require lifecycle handling, CSS, link services, storage wiring, and correct viewports—not merely instantiation. Add dirty/undo integration and linked-widget handling; explicitly defer or implement XFA, JavaScript calculations/validation, and submission actions.

16. **Major — Font and appearance ownership is unresolved (§4.3).** pdf-lib defaults to Helvetica/WinAnsi when regenerating form appearances; Unicode values can fail or change appearance. Choose which engine owns appearance generation, preserve valid pdf.js appearances, and embed appropriate fonts through `registerFontkit()` where needed. Bundled CSS fonts alone do not embed PDF fonts. [pdf-lib limitations](https://github.com/hopding/pdf-lib)

17. **Major — Common input files need Phase 1 safeguards (§2).** pdf-lib cannot decrypt encrypted PDFs; `ignoreEncryption: true` bypasses rejection, not encryption. Add password-open support through pdf.js, capability-based read-only mode, and detection of existing digital signatures before any rewrite. Preserve originals and require an explicit unsigned-copy operation when signatures would be destroyed.

18. **Major — Printing can omit form values (§4.6).** `AnnotationMode.ENABLE_FORMS` deliberately excludes widgets from canvas output. Print using `intent: 'print'` with `ENABLE_STORAGE` and captured `printAnnotationStorage`, or render a materialized output PDF. Include live annotations/signatures and honor print flags rather than compositing the screen indiscriminately.

19. **Major — Printing is neither bounded nor cross-platform exact (§4.6).** Five hundred Letter pages at 150 dpi require roughly 4.2 GB of decoded RGBA alone. Stream/spool pages with bounded memory, cancellation, and cleanup. Carry physical dimensions, await image decoding, and specify fit/actual-size, margins, mixed-size behavior, and printer tests; `webContents.print()` has platform differences, including macOS range limitations. [Electron printing](https://www.electronjs.org/docs/latest/api/web-contents)

20. **Major — History and crash recovery are overstated (§4.4).** Every page operation retains another full PDF; shallow array copies do not protect nested annotation objects. Form state is absent from snapshots. Use immutable commands/checkpoints, a memory budget, and complete form/page state. “Crash-free reload” requires a local recovery journal and external-file conflict detection.

21. **Blocker — IPC contradicts the claimed filesystem boundary (§4.7).** `file:open(paths)` and `file:save(path, bytes)` expose path-based authority despite the stated restriction. Replace paths with main-owned document capabilities; validate sender frame/window, argument schemas, byte limits, and destination grants for every privileged call. TypeScript types are not runtime authorization. [Electron security guidance](https://github.com/electron/electron/blob/main/docs/tutorial/security.md)

22. **Major — CSP needs an executable resource plan (§4).** `default-src 'self'` alone does not cover pdf.js-generated font URLs, image blobs, inline styles, or required WASM execution. Package the matching worker, CMaps, standard fonts, WASM, and layer CSS locally; specify minimal resource directives and test packaged offline builds. Explicitly constrain PDF JavaScript, external actions, navigation, downloads, and permissions.

23. **Major — Parent CSP does not constrain ad-network traffic (§6).** `frame-src` restricts which frame loads; the remote frame’s subresources follow its own policy. Opaque-origin sandboxing does not eliminate tracking or network requests. Apply host-side CSP and enforce network restrictions outside remotely changeable content; document IP/request exposure and state “no document backend” rather than unconditional “no server/no telemetry.”

24. **Major — Ad popups bypass the stated link architecture (§§4, 6).** `allow-popups-to-escape-sandbox` permits unsandboxed auxiliary pages; links do not automatically invoke the preload’s shell wrapper. Deny Electron child windows and route validated destinations through main. Prefer removing popup permissions and using a narrowly scoped click bridge that validates source, schema, and user action.

25. **Major — Ad compatibility and fallback are unproven (§6).** Literal `<iframe sandbox>` disables scripts, contradicting §4. Without `allow-same-origin`, storage-dependent clients and origin-sensitive requests can fail; iframe `load` also does not prove successful ad delivery. Specify one sandbox configuration and use a source-validated readiness/no-fill handshake with timeout fallback. [Iframe behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

26. **Major — Named networks do not establish approval (§6).** Hosting indirection does not make desktop inventory eligible. Obtain approval for the Electron placement, dimensions, sandbox, and refresh behavior. Carbon restricts refresh and format changes; EthicalAds discounts rapid repeated views. Start with direct/house ads until approved, and stop requests whenever the slot is hidden. [Carbon policy](https://www.carbonads.net/placement-policy), [EthicalAds policy](https://www.ethicalads.io/publisher-policy/)

27. **Major — Updater trust and lifecycle are incomplete (§8).** Require signed macOS and Windows releases, define Linux artifact authentication, protect release credentials, and publish architecture-correct manifests/artifacts together. Preserve dirty documents before installation; test actual upgrade paths, including macOS ZIP payloads. GitHub-hosted checksums alone do not provide independent publisher authentication. [Updater requirements](https://www.electron.build/v26/docs/features/auto-update/)

28. **Major — Phase 1 expectations need clearer boundaries (§2).** Add accessible keyboard/form navigation, screen-reader integration, clickable links, and reliable recovery to acceptance criteria. Explicitly defer comment replies/import/export, advanced forms, and browser-based signing. Existing-content editing is already Phase 3; market Phase 1 accordingly. Rectangles must never be presented as redaction.
